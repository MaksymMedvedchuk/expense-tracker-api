# Expense Tracker API

Навчальний pet-проєкт для 12-тижневого PDP (strong junior → Java backend).
REST API обліку витрат: категорії, статистика, конвертація валют, звіти.

## Стек
Java 21, Spring Boot 3, Gradle (Kotlin DSL), PostgreSQL, Flyway, JUnit 5 + AssertJ + Mockito.

## Команди
- Збірка з тестами і Checkstyle: `./gradlew build`
- Лише тести: `./gradlew test`

## Архітектура
- Пакети за фічами: `expense`, `category`, `user`, `common`
- Домен не залежить від Spring, JPA і web

## Режим навчання
Мета — розібратися в ООП, абстракціях, патернах і дженеріках.
- Перед реалізацією спитай мій варіант дизайну і оціни його, а не пропонуй одразу свій.
- Для кожного нового інтерфейсу, патерну чи дженеріка поясни: яку проблему він розв'язує і які є альтернативи.
- Не створюй інтерфейс без другої реалізації або межі з інфраструктурою — і скажи мені про це.
- Після змін коротко поясни ключові рішення.

## Git-flow
Гілки `feature/…`, `chore/…`, `fix/…`, `refactor/…`; conventional commits; PR ≤ 300 рядків; без пушів у main.

## Спілкування
- Відповідай українською; терміни і код — англійською
- Пояснюй коротко і по суті

## Робочий процес
Перед зміною файлів:
1. Поясни, як ти зрозумів задачу.
2. Перелічи файли, які зміняться.
3. Опиши план кроками.
4. Дочекайся мого погодження або правок. 

Читання коду і пояснення погодження не потребують.

- Найменша безпечна зміна; без рефакторингу, не пов'язаного з задачею.
- Зміна схеми БД — лише через нову Flyway-міграцію.

## Перевірка
- Після змін запусти `./gradlew build` і повідом точну команду та результат.
- Ніколи не стверджуй, що тести пройшли, якщо їх не запускали.
- Перед завершенням переглянь diff на випадкові зміни.
- Відокремлюй підтверджені факти від припущень.
